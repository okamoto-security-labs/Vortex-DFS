Engineering note / Runtime authorization

An approved tool is not an approved action.

Tool inventories establish what an agent can reach. They do not, by themselves, establish whether a specific request should execute. Vortex DFS explores that distinction through deterministic policy evaluation at a guarded execution boundary.

Vortex DFS · Experimental pre-alpha · Source-backed technical brief

The boundary

The Rust runtime evaluates a normalized request and its evidence against a policy. The resulting decision determines whether a protected executor is invoked. A rejected request must not cross that boundary.

What a practical MCP pilot should prove

Test scope

  • One agreed agent-to-tool workflow
  • Authorized and unauthorized actions
  • Missing or invalid authorization evidence
  • Attempts to bypass the enforcement path

Acceptance evidence

  • Reproducible outcomes and reason codes
  • Confirmation that denied actions do not execute
  • Observed false positives, not assumed zero
  • Integration overhead and residual risks

Current limitations

Vortex DFS remains experimental pre-alpha. Production MCP Tool Runner integration, production identity enforcement in the HTTP path, and immutable audit storage are not established capabilities in the repository README. Existing unit tests support the guarded-execution mechanism; they do not establish customer-environment efficacy or production readiness.

From mechanism to measured outcome

A paid, fixed-scope feasibility pilot would test this execution boundary against one real customer workflow. Scope, integration prerequisites, success criteria, and commercial terms would be agreed before any customer-specific development.
